# Milestone 003 — arcade HUD, musical countdown and four-beat movement

This is the current gameplay/presentation contract. It supersedes earlier beat-four movement lockout and post-combat suppression instructions. The existing root Godot project, fighter sources/resources, soundtrack, input map, ±70/±140 ms combat timing windows, 100 ms combination buffer and shared 44-pixel stick reach remain in place.

## Four-beat movement and deterministic combat

Every beat **1, 2, 3 and 4** samples held left/right input and applies at most one deterministic step. Release-before-boundary cancellation and arena/minimum separation constraints remain. Movement does not need an attack timing grade; a held direction can repeat on every boundary. A valid attack/block chord does not suppress it.

Beat four is an additional combat opportunity. Ordering is explicit:

1. Sample both players' held movement using the pre-boundary input state.
2. Apply both steps and collision/boundary constraints together.
3. Freeze the resulting positions once for that beat-four exchange.
4. Present action impact poses and accept combat combinations within the existing timing/buffering rules.
5. Adjudicate once against the frozen geometry after the late-input allowance closes.

A movement key pressed after the boundary queues for the next beat; it never moves retroactively. Rendering interpolation, late directional combinations or later position changes cannot change a frozen range result. Forward + execute remains MID, derived from facing. High/mid/low still share one reach. Regression tests cover an early-held advance that establishes contact and a late press that cannot turn a whiff into a hit at 120/140/160 BPM.

## Arcade presentation

`ArcadeHUD` is a full-viewport Control under its own CanvasLayer. It cannot transform fighter nodes or collision geometry. Two anchored, mirrored cards show RED/BLUE names, three coloured segments, small round-win markers and an initiative diamond. Warm cream/charcoal/red/royal-blue panels have hard pixel edges. The repository-authored 5×7 bitmap font is generated by `tools/build_arcade_font.py`; the PNG/FNT assets ship with the game and need no runtime Python or network access. Fighter artwork is not regenerated.

Energy is **derived**, not authoritative UI health: `Bout.energy_remaining(player) = 3 - hits[opponent]`, clamped to three segments. The resolver's hit counter already belongs to the scoring attacker. A clean strike updates the victim's card immediately; blocks, parries, timing misses, range whiffs and race wins remove no segments.

Top centre displays round/BPM/phase. Centre messages are temporary countdown or major outcomes. Lower-centre combat feedback uses HIGH/MID/LOW HIT, BLOCK, PERFECT PARRY and MISS. Menus/outcomes show relevant Enter/Escape instructions. Beat dots are hidden when they would overlap footer/help text. The arena stays clear during ordinary combat.

Raw state IDs, filenames, timestamps, latency, buffer/queue decisions and collision geometry remain behind F3, disabled by default. F3 switches to the diagnostic view; H displays player controls. The HUD's mouse-filter-ignore labels/panels do not consume gameplay input. Presentation never awards damage, advances a round or waits for a UI animation to resolve combat.

## Conductor countdown and race

The random anticipation phrase count remains. In the final phrase, the three preparatory beat boundaries display **3, 2, 1**; **GO!** begins exactly at the existing authoritative race cue, whether testing accent or drum cutoff. The number scale changes only in integer pixel increments derived from conductor time. There is no independent countdown timer or accumulated UI delta.

Anticipation instruction: `GET READY TO GRAB YOUR STICK!`. GO instruction: `GRAB YOUR STICK!`. GO clears after 350 ms, including when race resolution has already entered pickup, so the arena becomes visible. Inputs before the cue remain false starts; losing the race still gives no damage or round marker.

## Round and match controller

`MatchProgress` supplies the previously missing minimal match structure. `match_best_of` in combat settings defaults to **3**; two round victories secure the match. Positive odd best-of values are supported (an even setting is rounded up to the next odd value).

A round ends only at the existing three-clean-hit condition. MatchProgress accepts that round winner once, immediately adds one marker and optionally records the match champion. Existing finishing animation/audio presentation follows; it does not control scoring. ROUND WON and CHAMPION are distinct states/messages.

- Enter at menu: new match, scores cleared, round 1, full energy.
- Enter after ROUND WON: next round, fresh bout/energy/120 BPM, round markers retained.
- Enter after CHAMPION: rematch, markers cleared, round 1.
- Escape: menu.

Each round includes standoff/race again. A no-reaction/double-false-start race retry restarts only that bout and cannot erase prior markers or advance the round. Async finishing callbacks check the completed bout identity, preventing an old animation coroutine from changing a newly started round.

The new suite loads the actual main scene and verifies energy mapping, countdown boundaries at all tempos, false starts, no race damage/markers, clean diagnostic-free default UI, F3 visibility, both champions' full best-of-three progression, duplicate-award prevention, energy resets, preserved markers during race retries and deterministic beat-four movement/range. A footer/beat-dot overlap found during inspection was corrected.

Animation and audio preview scenes were smoke-launched successfully. Their underlying fighter/sound assets remain unchanged. Graphical/audio perceptual calibration is not implied by these UI tests; existing audio calibration limits still apply.
